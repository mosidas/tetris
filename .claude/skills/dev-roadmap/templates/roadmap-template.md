# roadmap.md テンプレート

`<workdir>/roadmap.md` の構成テンプレート。**参照による自己完結**を原則とする: 企画書・要求文書の内容を転記せず、章番号・見出しへの参照で解決する。unit の中身(API・データ構造・受け入れ基準)は書かない(dev-spec が各 unit の spec.md に書く)。

```markdown
# <roadmap 名> — 作業単位への分解

<この roadmap が何をできる状態にするかを 1〜3 文で書く。unit の切り方はこの状態から逆算している。>

<要求の本体がある場合はその所在を書く。例: 企画書の本体は `<パス>` にある。本書は企画書の内容を再記述せず、章番号で参照する。>

## 前提

- <着手時点で確定している事項。環境・技術選定・既存資産・運用の制約など。>
- <各 unit の仕様化で前提として扱える事実だけを書く。決まっていないものは「未確定」へ置く。>

## 1. unit 一覧

| #   | unit             | 範囲                                     | 依存 |
| :-- | :--------------- | :--------------------------------------- | :--- |
| 1   | `<slug>`         | <その unit で作るものを 1〜2 行で>       | —    |
| 2   | `<slug>`         | <同上>                                   | 1    |

順序は #1 → #2 → ... とする。<依存だけでは決まらない順序を選んだ場合は、その理由を書く。並行できる unit があればここに注記する。>

### 1.1. 各 unit の完了条件

- **`<slug>`**: <何が動けばこの unit が終わりかを、観測できる事象で書く。作業の完了(「実装した」)ではなく、確かめられる事象で書く。>
- **`<slug>`**: <同上>

## 2. 未確定

<いま問いを正確に述べられない項目を、述べられない理由とともに書く。問いを述べられるものは unit 一覧へ置く(答えを出す作業が調査であれば、調査を目的とする unit にする)。>

- **<項目>**: <なぜいま問いを述べられないか。>

## 3. スコープ外

<目的の外と判断した項目を理由とともに残す。削除すると同じ検討が再燃する。>

- **<項目>**: <目的の外と判断した理由。>
```

## 記入の注意

- **unit 名は作業ブランチ名になる**。他の roadmap の unit と重複しない語にする。
- **完了条件は観測できる事象で書く**。「〜を実装した」は作業の完了であり、動いたかを確かめられない。
- **未確定とスコープ外の項目を消さない**。未確定は unit 一覧へ移した時点で未確定の節から消し、スコープ外は残し続ける。
- 全 unit の完了後、未確定・スコープ外のうち以後も参照する項目は恒久情報(`../../dev-core/references/durable-info.md`)へ移す。移し終えてから roadmap を凍結する。
