# レビュー観点カタログ

dev-reviewer(敵対的判定器)に注入する観点(ペルソナ)の正本。呼び出し側(部品・composition)は作業内容に応じて観点を選び、**1 観点 = 1 起動**で dev-reviewer を並列 fan-out し、結果を保守的にマージする(1 観点でも `[Critical]` があれば全体不合格)。例外として、生成直後の一次検証(部品内蔵の文書ゲート。[doc-gate-prompt.md](../templates/doc-gate-prompt.md))は、文書ゲート系 3 観点を 1 体に包括する軽量形を用いる(観点別の並列パネルは composition の承認ゲートが担う)。

- 観点の追加・差し替えは、利用側プロジェクトの知識 port(`name: review-perspectives`。配置は自由、規約は [ports.md](./ports.md))で行える。port に同名の観点があれば port を優先する。
- 各観点の「重点」は網羅列挙ではなく検査の起点である。判定器は敵対的既定(不合格から出発し、立証できた項目のみ合格)で臨む。

出典: 観点の体系は [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) のペルソナ(code-reviewer / test-engineer / security-auditor / web-performance-auditor)の専門手順を取り込んで構成した。

## 目次

- 1. 返却契約(全観点共通の既定)
- 2. コード検証系の観点(requirements-conformance / structure / security / performance / test / runtime-smoke)
- 3. 条件付き観点(作業の特性で追加)
- 4. 文書ゲート系の観点(correctness / testability / completeness)

## 1. 返却契約(全観点共通の既定)

起動時プロンプトで上書きされない限り、次の構造化フィールドで返す。

- `ASPECT`: 担当観点名
- `VERDICT`: `APPROVED` | `REJECTED`(`REJECTED` は `[Critical]` が 1 件以上、または `UNVERIFIED` が `なし` 以外のときに限る)
- `FINDINGS`: 指摘の一覧。各指摘に `[Critical]`(合格を妨げる)/ `[Nit]`(軽微)/ `[FYI]`(観点外の気づき)を付け、箇所(ファイル・行・ID)と反する基準を明記する
- `UNVERIFIED`: 手段が無い・環境を起動できない等で実行できなかった検証項目の一覧。なければ `なし`。`なし` 以外のときは `APPROVED` を返さない(実行不能は不合格側に倒す)。呼び出し側はこのフィールドで欠陥(修正で解消する)と未検証(人間エスカレーションで解消する)を区別する
- `EVIDENCE`: 判定の根拠(実行したコマンド・照合した資料)
- `COVERAGE`: 照合の内訳。受け入れ基準(要件 ID)ごとに 1 行で ID と可否を書く。最終検証パネル・出荷ゲートの層では、照合した対象(テスト名・ファイル・観察結果)と立証の手段も書く(`EVIDENCE` が持つのは実行したコマンドと結果であり、合格の根拠を ID 単位で残すこの欄とは別にする)。照合していない ID には `未照合` と書く。要件 ID に紐づかない観点は、検証項目ごとに同じ形式で書く
- `DRIFT`: コード検証系の観点(2.)で見つかる、中間生成物(spec.md・tasks.md)の記述と実装・テストの食い違い。食い違いごとに、どちらが正しいかの判定と根拠、正しい解釈の置き場の候補([durable-info.md](./durable-info.md) 1. の配置先)を書く。中間生成物は書き換えない(凍結の規律)。なければ `なし`。欠陥を伴う食い違いは `FINDINGS` の `[Critical]` にも書き、この欄だけに書いて判定から外さない
- `RATIONALE`: 判定理由の要約

## 2. コード検証系の観点

実装後のコード(タスクレビュー・最終検証・出荷可否)に適用する。

### 2.1. requirements-conformance(要件整合)

- 対象: 実装・テストと、渡された受け入れ基準([notation.md](./notation.md) の要件 ID)
- 重点: 全受け入れ基準 ID が実装とテストに反映されているか(前方トレース)。要求されていない実装(スコープ外変更・過剰実装)がないか(後方トレース)。**申告のない**タスク境界(`_Boundary:_`)外のファイル変更がないか
- 境界外変更の扱い: 実装者が返却の申告フィールド(`OUT_OF_BOUNDARY`。フィールドの正本は起動時プロンプトの返却フォーマット)で「何を・なぜ変えたか」を申告した変更は、申告があること自体を欠陥としない。変更内容が受け入れ基準の達成に必要だったか、必要な範囲に収まっているかで判定する。**申告のない境界外変更は `[Critical]`** とする(タスク境界の意味が失われるため)

### 2.2. structure(コード構造)

- 対象: 変更されたコードの可読性・アーキテクチャ
- 重点: 命名と制御フローの明快さ。モジュール境界と依存方向の整合(内側が外側に依存していないか)。既存パターンとの一貫性。過度な抽象化・不要な間接層。コードの重複。コメントが Why not(採らなかった選択肢・コードから読めない制約)に限られているか(処理を言い換えるだけのコメントは指摘対象。[durable-info.md](./durable-info.md))。契約とドメインモデルの完全性([contract-and-domain.md](./contract-and-domain.md)): 不変条件を破れる公開状態(無条件 setter・公開ミュータブルフィールド)がないか、ドメインロジックがコントローラ・サービス層へ流出(貧血モデル化)していないか
- **モジュールの深さ**: 公開インターフェースの幅に対して内部の振る舞いの量が見合っているか。呼び出し側へ内部構造をそのまま露出する幅の広い浅いモジュール(引数・公開メンバが多く、内部で行う判断が少ない)を指摘する(出典: [John Ousterhout, A Philosophy of Software Design](https://web.stanford.edu/~ouster/cgi-bin/book.php) の deep / shallow module)
- **ファイルの肥大化**: 1 ファイルに責務が集中していないか。行数の機械的な検出は `check.py` が warning として出す(対象は tasks.md の「対象ファイル」に挙がった既存ファイルに限る。[static-check.md](./static-check.md))。指摘するのは行数そのものではなく、分割できる責務の境界が実在することとする

#### スメルのベースライン

リポジトリが規約を文書化していない場合も、次の 12 種を検査の起点にする。出典のカタログはこれより多くのスメルを収めるが、ここには**変更差分の読解だけで判定できるもの**を採る(実行時の観測や履歴の追跡を要するものは他の観点が担う)。各項目はハードな違反ではなく**名前付きの判断材料**であり、指摘には「なぜこのコードで問題になるか」を添える。2 つの拘束を伴う。

- リポジトリの文書化された規約(コーディング規約・知識 port)が本表より優先する。
- フォーマッタ・リンタが機械的に強制する項目は指摘しない(検査の重複になる)。

| スメル                  | 何であるか → 修正の方向                                                        |
| ----------------------- | -------------------------------------------------------------------------------- |
| Mysterious Name         | 意図が読み取れない名前 → 役割を表す名前に変える                                  |
| Duplicated Code         | 同じ構造の重複 → 1 箇所へ抽出する                                                |
| Feature Envy            | 他オブジェクトのデータばかり使う関数 → データを持つ側へ移す                      |
| Data Clumps             | いつも一緒に現れる値の組 → 1 つの型にまとめる                                    |
| Primitive Obsession     | ドメイン概念を primitive で表す → 値オブジェクト・列挙で表す                     |
| Repeated Switches       | 同じ分岐条件が各所に散る → ポリモーフィズム・対応表に置き換える                  |
| Shotgun Surgery         | 1 つの変更が多数のファイルへ波及する → 関連する振る舞いを 1 モジュールへ集める    |
| Divergent Change        | 1 モジュールが別々の理由で変更される → 変更理由ごとに分ける                      |
| Speculative Generality  | 使われていない汎用化・拡張点 → 削除する                                          |
| Message Chains          | 呼び出しの連鎖でオブジェクトを辿る → 必要な操作を直接の相手に持たせる            |
| Middle Man              | 転送するだけの層 → 呼び出し側と実体を直接つなぐ                                  |
| Refused Bequest         | 継承した機能を使わない・無効化する → 継承をやめて委譲にする                      |

出典: [Martin Fowler, Refactoring — Catalog of Code Smells](https://refactoring.com/)(Bad Smells in Code)。

### 2.3. security(セキュリティ)

- 対象: 変更されたコードと、その信頼境界
- 重点は 6 領域を体系的に検査する:
  1. 入力処理: インジェクション(SQL/コマンド/パス)・XSS・安全でないデシリアライズ・ファイルアップロード
  2. 認証・認可: パスワード・セッション管理・IDOR(認可漏れ)・権限昇格
  3. データ保護: 秘密情報のハードコード・ログへの漏出・暗号化・PII の扱い
  4. インフラ: セキュリティヘッダ・CORS・依存ライブラリの既知脆弱性。依存の取り込み規律(直接の外部依存をバージョン固定しているか、lockfile を依存の正本として扱いレビュー対象にしているか、インストール時に実行されるスクリプトを許可制で管理しているか)。既知脆弱性の照合だけでは供給側の侵害を捉えられないため、取り込みの経路も対象にする(出典: [OWASP Top 10 A06 Vulnerable and Outdated Components](https://owasp.org/Top10/A06_2021-Vulnerable_and_Outdated_Components/)・[SLSA](https://slsa.dev/))
  5. 外部連携: Webhook 検証・SSRF・外部 API への過剰な信頼
  6. AI/LLM 機能: プロンプトインジェクション・ツールの過剰な権限。不可逆・破壊的な操作を行う機能を、エージェントが呼べるツール表面へ登録していないか(「呼ばない」という規範ではなく、呼べない構成になっているか)。環境の取り違え(検証環境と本番環境、模擬実行と実実行)を構造的に防いでいるか(環境ごとに別の資格情報を持ち接続先を固定しているか、同一の資格情報で両方へ到達できる構成になっていないか)(出典: [OWASP Top 10 for LLM Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/) の Excessive Agency)
- 信頼境界ごとに STRIDE を適用し、指摘は [OWASP Top 10](https://owasp.org/www-project-top-ten/)・CWE へマッピングする。悪用可能性を検証してから報告する(理論上の指摘と実証済みの指摘を区別する)

### 2.4. performance(パフォーマンス)

- 対象: 変更されたコードの実行効率と退行
- 重点: N+1 クエリ・無制限ループ・不要な再計算/再レンダリング・メモリリーク。性能目標が定義されている場合は主要パスを計測して照合する
- 計測の誠実さ(Metric Honesty): 計測値を捏造しない。実測か静的解析かの出所を必ずラベルする。実測できない環境では「potential impact」と明示する

### 2.5. test(テスト品質)

- 対象: 変更に伴うテストコード
- 重点: 実装ではなく振る舞いをテストしているか。操作の結果(状態・出力)を検証しているか。モックはシステム境界のみに限定されているか。異常系・境界値・並行性が検討されているか。契約([contract-and-domain.md](./contract-and-domain.md))が検証されているか(事前条件違反の拒否・事後条件・不変条件)。既存の振る舞いを守る回帰テストがあるか。テスト全体がグリーンか(差分外を含む)
- バグ修正のレビューでは、修正前に失敗するテスト(再現テスト)で立証されているかを確認する(Prove-It)

#### アサーションの検出力(変異注入)

適用する層は最終検証パネルと出荷ゲートとする(タスク単位のレビューは対象外。1 タスクの差分では受け入れ基準の全体が見えないため)。この限定は**レビューが判定のために変異注入を実行する**場面に掛かる。実装者が自分の書いたテストに対して行う検出力の自己点検(手順は dev-implement が定める)は、判定を下す層ではないためこの限定の対象外とし、下の 2.〜4. の変異の選び方と判定の規律をそのまま用いる。

テストがグリーンであることは、テストが欠陥を捉えることを示さない。受け入れ基準ごとに、**その基準を破る変更を入れるとテストが失敗する**ことを実行で立証する(「この基準を検証しているように読める」を合格の根拠にしない)。

1. **対象の特定**: 担当する作業単位の受け入れ基準(要件 ID)ごとに、それを検証していると主張するテストを挙げる。挙がらない ID はテストの不在であり `[Critical]` とする。
2. **変異の選択**: その基準の否定に当たる最小の改変を実装側へ 1 つ選ぶ。定数への固定(分岐で決まる値を 1 つの値へ固定する)・条件の反転(判定の反転・比較演算子の入れ替え)・境界のずらし(`<` を `<=` にする、上限を 1 ずらす)・副作用(通知の送出・保存・破棄)の呼び出しの削除・同じ型の引数の入れ替えから選ぶ。
3. **実行**: 変異を入れた状態で 1. のテストを実行する。実行する場所と同時実行の排他は [runtime-verification.md](./runtime-verification.md) §3.1 に従い、元の作業ツリーに変異を残さない。
4. **判定**: 1. のテストが失敗すれば、そのテストの検出力が立証される。**失敗しなければ、そのテストはその基準を検証していない**。テストの不在と同じ扱いで `[Critical]` とし、入れた変異と、テストが失敗しなかった理由(観測するケースの期待値が全件同じ値である・結果ではなく呼び出しの有無だけを観測している等)を指摘に書く。
5. **記録**: 要件 ID・入れた変異・テストの失敗の有無を返却の `COVERAGE` に書く。

- 変異は 1 基準につき 1 件とし、実行は 1. で挙げたテストに絞ってよい(差分外を含む全体のグリーンは重点の別項で確認する)。
- 変異を作れない基準(定数の宣言のみ等)は、`COVERAGE` に「変異なし」と理由を添えて書く。手段が無く実行できない場合(検証コマンドが動かない・複製も逐次実行も採れない)は `UNVERIFIED` に挙げる。
- 変異の当たりを静的に付けるなら、同じ観測点の期待値が全ケースで同じ値になっている箇所を先に洗う。その値へ固定する変異でテストが失敗しない候補である。

### 2.6. runtime-smoke(実行時スモーク)

- 対象: 変更後のアプリケーションの実行時挙動(起動・主要フロー・GUI の描画・認証の成立)
- 追加条件: 実行時挙動に影響する変更では必須で追加する(固定観点に準ずる)。外してよいのは実行面を持たない変更(ドキュメント等)のみ
- 重点: [runtime-verification.md](./runtime-verification.md) の検証項目(共通・GUI・認証)を、同リファレンスの手段(能力検出)で実際に実行して観察する。テスト・ビルドのグリーンを実行時成立の根拠にしない。実行できない項目は返却の `UNVERIFIED` フィールドに列挙する(1. の規約により APPROVED を返せない)

## 4. 文書ゲート系の観点

中間生成物(spec.md・tasks.md 等)の承認ゲートに適用する。

### 4.1. correctness(正しさ)

- 重点: 上流(依頼・上流成果物)の意図と内容が一致しているか。事実・参照(ID・パス)が実在するか。論理矛盾がないか。体裁が整っていることを合格の根拠にしない

### 4.2. testability(検証可能性)

- 重点: 受け入れ基準・完了条件が検証可能な形(測定可能・二値判定可能)で書かれているか。曖昧語([notation.md](./notation.md) §4)が残っていないか。1 基準 = 1 検証可能な振る舞いか

### 4.3. completeness(網羅性)

- 重点: 異常系・エッジケースが検討されているか。スコープ境界(やらないこと)が明示されているか。未解決マーカー(`[要確認:]`・`UNVERIFIED`)が残っていないか。下流が作業を開始できる自己完結性があるか
