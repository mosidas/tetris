# レビュー指摘の受け取り

レビューの指摘(dev-reviewer の `FINDINGS`、最終検証パネルの `FINDINGS`、CI の失敗、人間のレビュー)を受けて修正する側の規律の正本。指摘を出す側の規律は [review-perspectives.md](./review-perspectives.md) が持つ。

出典: [obra/superpowers](https://github.com/obra/superpowers) の receiving-code-review(指摘は技術的に評価するものであり、同意の表明で応じるものではない)。

要請レベルは RFC2119 に対応する日本語の語句(しなければならない = MUST、する必要がある = SHOULD、してもよい = MAY)で表す。

## 1. 着手の前提

- **意味の取れない指摘が 1 件でもある場合、理解できた項目も含めて着手しない**。指摘は互いに関係しうるため、一部だけを先に直すと、後から判明した指摘と食い違う実装になる。不明点を先に解消し、全項目を揃えてから順に処理しなければならない。
- **指摘は主張であって根拠ではない**。実装の前に、対象のコードで成立するかを確かめる。確かめる項目は、既存の振る舞いを壊さないか、現在の実装がそうなっている理由が別に無いか、対象の言語・フレームワーク・バージョンで成立するか、指摘者が見ていない文脈が無いか、の 4 つとする。
- **確かめられない指摘は、確かめられないと明示する**。「何が分かれば判定できるか」を添えて呼び出し側へ返す。推測で実装してはならない。

## 2. 押し返す条件

次のいずれかに当たる指摘は、実装せずに技術的な根拠を添えて押し返す。

- 既存の振る舞いを壊す。
- 使われていない機能に対する「きちんと実装せよ」という要求である。実装の前に使用箇所を検索し、使用が 0 件なら実装ではなく削除を提案する(YAGNI)。
- 対象のバージョン・プラットフォームで成立しない。
- 承認済みの仕様・設計の決定と矛盾する。この場合は自分でどちらかを選ばず、論点を呼び出し側へ返す。

押し返しは技術的な根拠(検索結果・テストの実行結果・バージョンの確認)で行う。防御的な言い回しをしない。押し返しが誤っていたと分かった場合は、事実を 1 行で訂正して実装へ移る。弁明と経緯の説明を書かない。

## 3. 処理の順序

1. 不明点を解消する(1.)。
2. 修正を、(a) 壊れているもの・セキュリティに関わるもの、(b) 単純な誤り(誤字・import・型)、(c) 構造の変更を伴うもの、の順に行う。
3. 1 件ごとに検証する。まとめて直してまとめて検証しない(どの修正が何を解消したかを判定できなくなる)。
4. 差分の外の回帰を確認してから完了を報告する。

## 4. 応答の形

- 指摘への同意を賛辞・謝辞で表さない。直した事実と箇所を書く。応答の目的は、指摘が解消されたことを判定できる形で示すことにある。
- 指摘の内容を自分の言葉で言い直して確認するか、直して差分で示す。「対応します」という表明だけを返さない。

## 5. サブエージェントへの反映

この規律のうち再投入される実装者に掛かる部分は、`../../dev-implement/templates/implementer-prompt.md` の `<review_findings>` の節が要約して持つ。同節は本ファイルの安全エコーであり、規律の追加・変更は本ファイルで行う。
